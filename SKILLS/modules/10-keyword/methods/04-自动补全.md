# 方法 D：前台自动补全

> 导图子项：前台自动补全
> 方法来源：`nexscope-ai/Amazon-Skills` 的 `amazon-keyword-research`

**这是唯一能反映"当下真实搜索行为"的免费数据源。** 卖家精灵的搜索量是按月估算的，自动补全是实时的——买家今天在搜什么，它今天就能看到。

---

## 接口

```
https://completion.amazon.com/api/2017/suggestions?mid={市场ID}&alias=aps&prefix={前缀}
```

**硬限制：每次只回 10 条。** 实测加 `&limit=40` 无效，接口不接受该参数。

所以只能靠前缀组合凑量。

| 站点 | mid |
|---|---|
| US | ATVPDKIKX0DER |
| UK | A1F83G8C2ARO7P |
| DE | A1PA6795UKMFR9 |
| FR | A13V1IB3VIYZZH |
| IT | APJ6JRA9NG5V4 |
| ES | A1RKKUPIHCS9HS |
| JP | A1VC38T7YXB528 |

CA / AU / IN / MX 未实测，`ac.py` 会直接拒绝，不要猜。

**本机只能用 `web_fetch` 调**——shell 里没有外网（`curl` 到 amazon.com 直接超时）。

---

## 29 次请求法（nexscope 原版）

一个种子词展开成 4 组前缀：

| 组 | 前缀 | 次数 | 捕获 |
|---|---|---|---|
| 原词 | `{seed}` | 1 | 主干长尾 |
| 商业前缀 | `best {seed}` / `cheap {seed}` / `top {seed}` | 3 | 比价、决策型意图 |
| 字母后缀 | `{seed} a` … `{seed} z` | 26 | 补全所有后续长尾 |

**1 + 3 + 26 = 29 次 × 10 条 = 290 条原始结果，去重后约 100–200 个词。**

这是 nexscope 的原始设计，也是当前唯一能凑到百词量级的办法。

---

## 本机怎么跑

### 1. 生成请求清单

```bash
# 完整模式（29 次）
python scripts/ac.py plan --seed "coat rack" --marketplace US --out plan.json

# 精简模式（1 + 3 + 10 个高信息量字母 = 14 次）
python scripts/ac.py plan --seed "coat rack" --marketplace US --mode fast --out plan.json
```

`plan.json` 里每条都带现成的 URL，直接拿去 `web_fetch`。

### 2. 逐个调用

对 `plan.json` 里的每个 `url` 调一次 `web_fetch`，把返回的 `suggestions` 数组按顺序收进结果文件：

```json
[
  {"prefix":"coat rack",   "position":1, "value":"coat rack"},
  {"prefix":"coat rack",   "position":2, "value":"coat rack wall mount"},
  {"prefix":"best coat rack","position":1,"value":"coat rack wall mount"}
]
```

`position` 就是数组下标 + 1。**位次越高 = 搜索热度越高**，这是免费的排序信号。

### 3. 合并去重

```bash
python scripts/ac.py merge --in results.json --out suggestions.csv
```

输出按 `ac_score` 降序，`ac_score = (11 - 最佳位次) × 10 + 命中前缀数 × 3`。

**为什么这么算**：位次反映热度，命中前缀数反映稳定性。一个词在 5 个不同前缀下都排第 1，比只在 1 个前缀下排第 1 可信得多。

## 预算控制

29 次 `web_fetch` 不便宜（每次一个工具调用），按场景选模式：

| 场景 | 模式 | 次数 | 产出 |
|---|---|---|---|
| 首次调研一个新品 | full | 29 | 100-200 词 |
| 已有基础词库，只补长尾 | fast | 14 | 40-80 词 |
| 多站点对比 | 每站 fast | 14 × N | 逐站对比 |
| 只验证某个词有没有搜索 | 单次 | 1 | 10 词 |

**种子词怎么选**：取方法 B 的 `weighted_score` Top 3。不要用自己拍脑袋想的词——那等于用假设验证假设。

## 结果怎么用

### 1. 位次当热度代理

没有搜索量，但有位次。第 1 位和第 10 位的热度差可能是几十倍。

在合并阶段，`ac_score` 只用来**排序和补位**，不参与 `W` 的计算（除非该词在 `keyword_miner` 里查不到搜索量，此时用 `ac_score` 做代理并标 `EST`）。

### 2. 识别问题型词

自动补全最容易出问题型长尾，这是别的方法拿不到的：

| 模式 | 例 | 用途 |
|---|---|---|
| `{seed} for ...` | coat rack for entryway | 场景词，进五点第 3 点 |
| `how to ...` | how to install coat rack | QA 素材 |
| `{seed} that ...` | coat rack that holds heavy coats | 痛点词，进五点第 2 点 |
| `{seed} without ...` | coat rack without drilling | **强痛点，最高价值** |

"without / that / for" 开头的这三类，直接喂给 `30-insight` 做用户问题库。

### 3. 剔除品牌词

自动补全里会混进竞品品牌（搜 "coat rack" 出 "coat rack umbra"）。这些单独归到 BRAND，不进机会词。

## 常见坑

| 坑 | 表现 | 解法 |
|---|---|---|
| 中文种子词 | 返回空或乱码 | 种子词必须是英文 |
| 大小写 | 不影响结果，接口会归一 | — |
| 特殊字符 | `&` `+` 会被截断 | URL 编码，`ac.py` 已处理 |
| 缩写词 | "coffee mkr" 这种返回很少 | 用完整词做种子 |
| 跨站差异 | 同词在 DE 和 US 结果完全不同 | 一站一跑，不要复用 |

## 输出

`suggestions.csv`：

| 列 | 含义 |
|---|---|
| `keyword` | 归一化后的联想词 |
| `best_position` | 在哪个位次出现过最高 |
| `hit_count` | 总共被返回几次 |
| `prefix_count` | 被几个不同前缀命中 |
| `ac_score` | 综合热度分 |
| `prefixes` | 命中的前缀列表（可回溯） |

**`prefixes` 列很重要**：如果一个词只在字母后缀里出现，说明它是窄长尾；如果原词和 best 前缀都命中，说明它是主流词。
