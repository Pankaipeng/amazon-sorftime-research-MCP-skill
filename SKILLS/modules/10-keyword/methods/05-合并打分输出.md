# 合并、打分、输出

四路跑完后，这一步把碎片拼成能用的东西。

---

## 一、合并去重

### 归一化

```
小写 → 去标点 → 合并多余空格 → 去首尾空格
```

`Shoe Rack` / `shoe  rack` / `shoe-rack` 归为同一个词。

**不合并单复数**："hook" 和 "hooks" 在 Amazon 索引里是分开的，合并会丢信息。但报告里要注明这条规则。

### 来源标记

每个词记一个 `sources` 字段，多个来源按字母顺序拼在一起（如 `ADNS`）：

| 标记 | 来源 | 可信度含义 |
|---|---|---|
| `A` | 竞品流量词 / 出单词 | 有真实曝光或转化 |
| `B` | 竞品标题词频 | 有行业共识 |
| `C` | 竞品五点词频（`features` 字段） | 有卖点表达；默认只给已发现的词补证据，不单独发现词 |
| `D` | 前台自动补全 | 有真实搜索行为 |
| `S` | 卖家精灵 `keyword_miner` 搜索量 | 有量，但**这一路主要供"量"，不是"发现词"的方法**；只在 S 里出现的词属单源，可信度最低 |
| `N` | 商机探测器（Niche 搜索词表） | 官方口径，有搜索转化率 |
| `E` | ABA 热门搜索词 | 官方排名，只有排名没有绝对值 |

> **为什么要拆 N 和 E**：两者都属"后台报表"，但 Niche 给的是搜索量与转化率，ABA 给的是排名与点击份额，用途不同，合并成一个 `E` 会看不出这个词到底被哪张表证实过。
>
> **为什么要单列 S**：搜索量是补量环节的副产品，不是发现新词的渠道。实测 235 个词里有 35 个只出现在 S 里——前四路都没抓到，只有一个搜索量数字，这种词要标"单源"。

**多源本身是强信号。** 字母越多越可信：`ADNS`（四路见过）远强于 `S`（只有搜索量）。在最终评分里可以给个小加成：`源数 ≥ 3` 时 R 加 0.05，上限 1.0。

## 二、补指标

搜索量未知的词，批量丢给 `keyword_miner`：

```python
mcp__ss_mcp__keyword_miner({
  "request": {
    "marketplace": "US",
    "keywordList": ["词1","词2","..."]   # 一次 ≤50 个
  }
})
```

取回字段：

| 字段 | 含义 | 用途 |
|---|---|---|
| `searches` | 月搜索量 | W 的主因子 |
| `purchases` | 月购买量 | 校验需求真实性 |
| `purchasesRate` → 实际字段 **`purchaseRate`** | 购买率 | 转化意图强度 |
| `spr` | 上首页所需销量/评论 | 进入成本 |
| `titleDensity` | 标题密度 | 竞争饱和度 |
| `monopolyClickRate` | 点击集中度 | 是否被头部垄断 |
| `bid` | PPC 建议竞价 | 广告成本 |
| `avgPrice` | 均价 | 价格带判断 |
| `supplyDemandRatio` | 供需比 | 蓝海判断 |

**查不到的词**标 `EST`，用 `ac_score` 做代理，不要编数字。实测 `keywordList` 精确查询 32 个词，有 7 个返回 `searches: null`（纯长尾），属正常。

### 搜索量是月度值，底表必须锁死一期

`searches` 每个月都会变，而且变的不只是小数——实测同一批词隔一个月，`faucet rack` 从 1,604 涨到 9,932（+519%）、`sink organizer rack for kitchen` 从 9,202 涨到 28,198（+206%）。113 个词里 30 个和当月值对不上，其中 26 个是 −12% 到 −30% 的衰减。

后果很直接：W 是搜索量乘出来的，掺了不同月份的数据，排序就是假的。更坑的是**看不出来**——`source` 列写着 `keyword_miner 2026-10`，但值其实是上一期的，"标签比数据可信"。

规矩三条：

1. **底表只存一期**，期次写进每行的 `source`（如 `keyword_miner 2026-10`），换期就整表重刷，不要"只补新词"。
2. **每轮开跑前抽查 10 个词**，和当月官方值对一遍。有一个对不上，就说明整表要刷。
3. **不要在代码里写死任何搜索量**。补量结果必须落成 `06-搜索量底表.csv`，脚本只读文件。

### 竞争度数据只对"会进四象限的词"有要求

`07-竞争度底表.csv` 里四个指标（spr / monopoly_click_rate / title_density / products）不是每个词都要有。需要它的只有 **P0/P1/P2 里的实测词**——否定词、品牌词、观察词根本不会进四象限，给它们补数据是白跑。

实测海绵架：113 个实测词里 9 个品牌词 + 20 个否定词 + 6 个观察词，真正需要竞争数据的只有 78 个。所以判断"覆盖率够不够"要用 78 当分母，不是 113。分母用错会让人以为缺了 34 个，实际只缺 7 个。

## 三、口径校验

导图上写了"多口径用于数据校验，结果需去重处理"。具体怎么做：

### 四个口径的关系

| 口径 | 来源 | 特征 | 拿不到时 |
|---|---|---|---|
| 卖家精灵 | `keyword_miner` | 月粒度估算，覆盖广 | — |
| ABA | 品牌分析 | 官方搜索频率排名，只有排名没有绝对值 | 标 `DATA_MISSING` |
| 后台商机探测器 | 卖家后台 | 类目推荐词，含搜索量区间 | 标 `DATA_MISSING` |
| **自有后台报表** | **用户上传的附件** | 自己的曝光、点击、**订单**、退货 | 标「后台数据：未提供」 |

**前三个是市场侧，第四个是自己的账户侧。四个都不能相加，也不能互相替代。** 差值 3-5 倍是常态。

第四行要特别说明：卖家精灵 MCP **拿不到**你店铺的广告报告和业务报告，这部分必须由用户导出后上传（见 `00-input/README.md` 第 3 节）。它对准确性的影响最大，因为它是唯一带真实转化的数据。

### 校验规则

| 情况 | 处理 |
|---|---|
| 卖家精灵有值、ABA 排名也靠前 | 高可信，正常用 |
| 卖家精灵有值、ABA 查不到 | 可能是长尾或新词，标"单源" |
| 卖家精灵无值、ABA 有排名 | 用 ABA 排名做相对排序，搜索量标 `EST` |
| 两者趋势相反 | **危险信号**，报告里单独提，不要下结论 |
| **后台报表有订单 + 卖家精灵有搜索量** | 双向印证，**直接进 P0**，优先级高于纯估算词 |
| **后台报表有曝光、订单为 0** | 否定候选，**优先于模型判断**（真金白银试过的结论） |
| **后台报表有、卖家精灵查不到** | 新词或超长尾，用报表数据兜底，标 `sources=E` 单源 |
| **后台报表没传** | 不阻塞，但口径声明里写清"转化类结论未验证" |

### 只在报告里写一句

```markdown
口径校验：137 个词中，112 个有卖家精灵搜索量；
其中 89 个在 ABA Top 100k 内，方向一致；
3 个出现方向背离（见附录），已标注但不用于决策。
```

## 四、相关性 R

```
R = 0.5 × R1 + 0.3 × R2 + 0.2 × R3
```

| 分量 | 判定 | 打分 |
|---|---|---|
| **R1 品类相关** | 词是否直接指向本品品类 | 1 = 是；0.5 = 相关品类；0 = 否 |
| **R2 属性匹配** | 词里的属性与本品事实卡是否一致 | 1 = 一致；0.5 = 部分；0 = **冲突** |
| **R3 市场共识** | = 竞品标题覆盖率（拿词逐条比对 `02b-竞品标题原文.csv`） | `min(1, coverage / 0.6)` |

**R3 的计算方式必须是"精确包含"，不能读预计算的 n-gram 表。** 标题词频表只统计到 3 个词的组合，超过 3 个词的短语就取不到值，取不到就给中性 0.5——实测 235 个词里有 **210 个（89%）** 卡在这个占位分上，其中实测词 97/113。也就是说相关性里那 0.2 的权重，九成的时候是凭空给的 0.1 分。这不是小瑕疵，是整列数据在空转。

正确做法：把 30 条竞品标题原文整条存下来，拿候选词去逐条比对——把词拆成实词（去掉 for / and / the / with / of / in / on / to / a / an），看一条标题是否**完整包含**这些实词，顺序不限；30 条里命中几条就是覆盖率。分词时两个细节不能省：**去标点**（否则 `kitchen,` 和 `kitchen` 算两个词）、**复数折回单数**（`sponges` 算 `sponge`）。这两步不做，`sponge holder for kitchen sink` 会被算成 0.6，做了是 0.87。

**R3 要归一化，不能直接把覆盖率当 R3。** 泛词覆盖率能到 0.9，长尾只有 0.2。直接拿 coverage 当 R3，长尾词会被压到 0.6 以下，全部掉进 P2/P3，明明更精准的词反而排最后。

约定 **覆盖率 60% 记满格**（`min(1, cov/0.6)`）：出现在 6 成竞品标题里就算行业共识，再多也不加价。

> 实测（壁挂海绵架，30 条标题）：`sponge holder for kitchen sink` 覆盖率 0.87 → R3=1.0；`sink caddy` 0.63 → R3=1.0；`kitchen sink accessories` 0.11 → R3=0.185；`rv kitchen essentials` 0.00 → R3=0。

**真的没有覆盖率数据时 R3 给 0.5**（中性），不要给 0——那不是"没有共识"，是"没测"。但这条只该在缺输入文件时触发。如果跑出来大面积是 0.5，先查是不是还在读 n-gram 表。

**这条修完之后要反过来看一遍旧结论**：实测里有三个词（`rv kitchen essentials` / `bathroom sink accessories` / `farmhouse sink accessories`）此前靠 0.5 的中性分白捡了 0.10 的相关性，实际 30 条壁挂标题里一条都没写它们。修完 R 从 0.65 掉到 0.55。占位分既会冤枉人，也会帮错人。


**R1 或 R2 为 0 的词直接进否定清单**，不参与后续排序。典型冲突：

- 本品 wall mount，词是 freestanding → R2=0
- 本品 wood，词是 metal → R2=0
- 本品透明，词是 black / matte black → R2=0（实测案例：本品 Clear，`black kitchen accessories` 月搜 10,064，必须否掉）
- 本品 5 hooks，词是 8 hooks → R2=0.5（相关但不同规格）

### R2 里不放「形态」（本技能的范围外）

形态（安装方式）是买家最先筛掉的那一维，这一点没变。但**形态不能靠词面判断**：`sponge holder for kitchen sink` 这个词本身不带 wall / countertop，可搜索结果里两种形态混着。要判形态，得看"这个词底下排在前面的商品是什么"，那是商品属性分类的活，不是关键词词面能推出来的。

所以本技能的 R2 **只判词面上能确认的材质、颜色、属性冲突**（metal / bamboo / black / soap dispenser 这类）。`config.yaml` 里留了 `form.enabled: false` 的开关和两套词表，但默认关闭，不参与打分。需要形态维度时，由独立的「商品属性分类」skill 先给商品打标签，再把标签回填进词库的 `form` 列——路径是"商品→标签→词"，不是"词→猜形态"。

> 这一条是踩过坑才改的：早期版本在 R2 里加了形态词表，判定为"泛词（形态混合）"的词统一给 0.5。结果是 235 个词里绝大多数都进了 0.5，R2 这一列失去区分度；更糟的是它把分层和相关性绑在一起，撤掉形态维度后全员 R ≥ 0.8，"大词"整档消失。详见第六节的解耦说明。


**R1/R2 是判断不是数据，必须写依据。** 报告里每行标 `JUDGED: 依据=...`。

## 五、权重 W

```
有搜索量：  W = searches × R
无搜索量：  W = ac_score × R × 10        （EST 词，把 ac_score 拉到千级量级）
```

为什么用乘积：搜索量再大，相关性为 0 就是 0 分。加和会让大词永远排第一。

**W 只用于排序，不要拿绝对值比较不同类目**——不同类目的搜索量基数差一个数量级。

## 六、分层（导图输出层之一）

**层级只看这个词有多宽，和相关性 R 完全无关。** 四档，不是三档。

档位的切法有三种，写在 `config.yaml` 的 `tiers.mode` 里，默认 `head_relative`：

| 模式 | 切法 | 什么时候用 |
|---|---|---|
| **head_relative**（默认） | 以本类目最大词为 100%，≥30% 大词 / ≥10% 中词 / ≥3% 小词 / 其余长尾 | 换类目不用改参数，自动适配类目大小 |
| **volume_absolute** | 固定绝对锚：≥10 万大词 / ≥3 万中词 / ≥5 千小词 / 其余长尾 | 跨类目口径要统一时用，但小类目会被压成全是长尾 |
| **percentile** | 按词库自身分位 P80 / P50 / P20 | 词库规模稳定时可用，扩容就漂 |

另有 `tier_abs` 一列，用 ABA 搜索频率排名做**全站统一标尺**（≤1 万大词 / ≤10 万中词 / ≤50 万小词），跨类目可比。没有 ABA 排名时退回类目内层级。

没有搜索量的词（EST / NODATA）层级留空，不硬分。

**为什么默认用头部比例而不是绝对锚。** 实测按大盘设 10 万/3 万/5 千，这个类目最大词才 167,620，`sponge holder for sink`（21,755 搜索、转化 5.33%）被压成"小词"，再叠高竞争直接判成"不建议打"——而它是壁挂件最精准的词之一。改成头部比例锚之后它落回中词。**绝对锚必须配全站可比的指标（ABA 排名），配搜索量就会随类目大小失真。**

**为什么必须和 R 解耦。** 早期版本写的是「大词 = 搜索量 ≥ P75 且 R < 0.8」。这套规则把两个维度绑在一起，一旦相关性算法调整，层级就跟着塌——实测把形态维度去掉后，全员 R ≥ 0.8，"大词"直接消失，整个分层归零。层级是客观的宽度，不该被主观打分污染。

**阈值必须写进报告**，让看的人知道"大词"在这个类目里具体指多少搜索量。

## 七、优先级（导图输出层之二）

按 W 降序，**名额制**：

| 档 | 判定 | 动作 |
|---|---|---|
| **P0** | W 排名前 `p0_slots` 个（默认 3） | 标题、Highlights |
| **P1** | 之后 `p1_slots` 个（默认 27） | 五点、A+ |
| **P2** | 其余 | ST、QA、观察 |
| **BRAND** | 竞品品牌词 | 单列，不否定、不投广告、不进标题 |
| **OBSERVE** | R1=0 但过于宽泛 | 只观察，不进否定 |
| **NEG** | R1=0 或 R2=0 | 否定清单 |
| **NODATA** | 无搜索量也无补全位次 | 待补量，不排序 |

**为什么改名额制**：早期用「W 前 10 + R≥0.8 + 转化率≥2%」三重条件，实测叠下来只剩 3 个词进 P0，其余 232 个全挤在 P1/P2，既不可控也无法解释"为什么是这 10 个"。

名额制把"要几个"交给运营（`p0_slots`，按类目行情定），算法只负责排序。这样 P0 永远是一个可执行的数量，而不是被三条规则随机筛出来的残渣。

**搜索转化率退出排序。** 它保留在词库里作展示列，帮助判断"这个流量纯不纯"，但不再当 P0 的否决票。理由：新品期泛词的高搜索量本身就是价值，用转化率一刀切会把入口关掉。想启用的话改 `config.yaml` 里的 `use_conversion_veto: true`。

**BRAND 必须真正产出。** 早期只在文档里定义了这一档，实现里从没产生过，结果 `scrub daddy holder`（月搜 82,968）、`scrub mommy holder`（15,543）、`oxo sponge holder` 全混在正常词库里。品牌词是不是机会，是"要不要抢竞品流量"的独立决策，不该由关键词评分替它做。识别方式：用竞品池的 brand 列 + `config.yaml` 的 `brand_extra` 做短语/单词匹配。

**EST 词最高 P2**，一律排在 MEASURED 之后，理由见第十节。

## 九、质量检查

交付前逐条过：

## 十、两条硬规则（2026-11-13 实测补充）

### 1. EST 词不参与 P0/P1

`keyword_miner` 查不到搜索量的词，用 `ac_score × R × 10` 估个 W 是可以的，但**这个 W 和实测 W 不是一个量纲**，不能混在一张榜上排序。

实测：118 条自动补全词里有 111 条查不到搜索量。如果让它们和实测词一起排，`ac_score` 高的长尾会压过真实有量的词。

处理：

```
有搜索量 → MEASURED，正常参与 P0-P3
只有 ac_score → EST，最高给 P2，一律排在 MEASURED 之后
两样都没有 → NODATA，单列"待补量"，不参与排序
```

**EST 占比超过 40% 要写进报告**，并说明原因（通常是方法 D 采集过宽，或品类本身搜索量极低）。别装作词库里全是实测词。

### 2. 太泛的词不能进否定清单

R1=0 只说明"不是本品"，不说明"该否定"。**否定一个比本品更宽泛的词，会连正常流量一起挡掉。**

实测踩过的坑：`kitchen sink`、`suction cup`、`stainless steel`、`adhesive strips`、`smiley face` 都算 R1=0，但它们是把整个类目都包住的大词。放进否定清单等于关掉一半入口。

处理：设一个 `NO_NEG` 白名单，这类词标记"观察"，不进 `negative_words.txt`。

**进否定的三类才安全**：对立形态（countertop / tray / freestanding）、冲突属性（材质、颜色、尺寸）、异类商品（soap dish / cleaning caddy）。

**反向的一条（2026-11-13 运营判定）**：`faucet rack` 月搜 9,932、量在涨，但业务判它不算相关，R1 记 0 进否定。**量的变化不能反过来改相关性判断**——搜索量是月度波动的，R1 问的是"这个词底下卖的是不是同一类货"，两者不能互相覆盖。

## 十一、合并追踪（证明每条路真的被消费）

词库交付时必须附一张 `00-五路合并追踪.csv`，逐路写清：产出多少词、进了候选多少、进了词库多少、其中多少进了 P0/P1、多少进了否定。

不附这张表的词库**无法验证是不是真的合并过**——最常见的问题是：方法 B/C/D 各自出了 CSV，但最终词库其实是人工维护的清单，三份产出根本没进去。

实测（壁挂海绵架，262 条产出 → 235 条入库）：

| 来源 | 产出 | 进词库 | 进 P0/P1 | 进否定 | 单源 |
|---|---|---|---|---|---|
| A 竞品流量词 | 15 | 15 | 12 | 1 | 1 |
| B 标题词频 | 45 | 19 | 5 | 0 | 2 |
| C 五点词频 | 285 | 23 | 11 | 1 | 0 |
| D 自动补全 | 118 | 118 | 1 | 31 | 111 |
| S 搜索量底表 | 113 | 113 | 30 | 27 | 34 |
| N 商机探测器 | 20 | 20 | 20 | 0 | 0 |
| E ABA | 41 | 41 | 6 | 9 | 1 |

**这张表本身就是结论**：五路重合度极低。C 路 285 条只有 23 条进词库——五点里大部分是句子成分，不是搜索词，所以它默认只做证据、不做发现（`c_listing_mode: support_only`）。D 路 118 条只有 1 条进得了 P0/P1——不是 D 没用，而是它拿到的是"真实存在但没搜索量"的长尾，战场在 QA/ST。如果某一路的"进词库"是 0，要么参数错，要么那一路没跑对。「单源」那列也要看：D 路 111 条是单源，意味着除了自动补全没人见过它。

## 十二、脚本与配置（v3.6）

算法到这里就结束了，落地靠三个文件，**不要在代码里调参**：

| 文件 | 职责 |
|---|---|
| `skills/scripts/config.yaml` | 唯一真相源：权重、分位、P0/P1 名额、转化率是否参与、EST 上限、各类词表、输入输出路径 |
| `skills/scripts/merge.py` | 读 config + 五路产出 → 分层 → 优先级 → 词库/否定/品牌词/追踪表 |
| `skills/scripts/check.py` | 7 项交付自检，不过不许交 |

```bash
python skills/scripts/merge.py <项目目录>
python skills/scripts/check.py <项目目录>
```

**评审红线：`merge.py` 里不允许出现任何硬编码的词或数字。** 出现就是缺陷，打回。

这条规矩是被前几版逼出来的：`score.py` → `score_v2` → `score_v3` → `build_library`，四份脚本层层叠加，词表写成常量 `S={...}`，阈值散在代码里。后果是方法 B/C/D 各出了 CSV，词库却只吃掉 3-5 个——因为打分根本只认那份手写词表。同一类问题在 `build_library.py` 里还小规模复发过一次（16 个覆盖率值直接写在代码里）。

`check.py` 的 7 项：词库字段完整 / 五路均有贡献 / EST 占比 / 否定清单无过泛词 / P0 名额 / BRAND 未混入 P0·P1 / 层级优先级取值合法。

**为什么要设门槛**：`EST 占比` 这一项在实测里真的拦下了 47%（上限 40%）。拦下之后不是改数字糊过去，而是要么回去提高 `ac_score` 门槛，要么在 config 里显式承认并写清原因——两条路都比"悄悄放过"强。

## 十三、形态判定为什么不在这里做

R2 只能判词面上的材质、颜色冲突（`stainless` / `black` 这种），判不了安装方式。`sink caddy`、`faucet rack` 这类词，光看字面分不清是台面款还是壁挂款。

早期试过用关键词表硬判（词里有 `suction` 就算壁挂、有 `countertop` 就算台面），能跑，但会误判，而且一旦关掉这个维度，R 全员 ≥ 0.8、分层直接失效——说明它本来就是临时补丁，不是可靠的判据。

正确做法是看"这个词底下卖的是什么货"：拉该词 Top 10-20 商品，数标题里壁挂/台面的比例，用比例当 R2。这属于商品属性分类，应该由独立的 skill 产出标签后回填。`config.yaml` 里 `form.enabled` 已预留开关，默认关闭。
